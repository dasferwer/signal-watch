# SignalWatch

[![Проверки проекта](https://github.com/dasferwer/signal-watch/actions/workflows/ci.yml/badge.svg)](https://github.com/dasferwer/signal-watch/actions/workflows/ci.yml)

Сервис анализирует события входа, регистрации и использования API. Он считает признаки за временные окна, сравнивает правила с Isolation Forest и сохраняет каждое решение вместе с признаками, порогами и версией модели. Оператор может отметить ложную тревогу, а повторный прогон проверяет воспроизводимость решений.

Это задание 14 из плана портфолио, папка 23. Стек: Python 3.12, FastAPI, PostgreSQL 17, RabbitMQ 4.1, Redis 7.4, scikit-learn, SQLAlchemy, Alembic и Docker Compose.

## Запуск

Нужен Docker с Compose. Для проверок на хосте нужны Python 3.12 и `uv`.

```bash
cp .env.example .env
make up
make smoke
```

API: [localhost:8230/docs](http://localhost:8230/docs). Модель уже лежит в `artifacts/`; приложение не скачивает веса и не обучает модель при запуске. Контейнер `migrate` завершается после миграции, остальные шесть сервисов продолжают работать.

После `make up` журнал пуст. `make smoke` отправляет 1 003 демонстрационные доставки: 1 002 уникальных события, один повтор и два примера опоздания. Он проверяет тревоги, ручную проверку и совпадение решений при воспроизведении. Данные сохраняются; повторный запуск не создаёт копии исходных событий.

## События

Для отправки нужен `X-Ingest-Token`, для просмотра решений и повторного прогона — отдельный `X-Admin-Token`. Демо-токены находятся в `.env.example`.

```bash
curl -sS http://localhost:8230/events \
  -H 'Content-Type: application/json' \
  -H 'X-Ingest-Token: local-demo-signalwatch-ingest-change-before-deployment' \
  -d '{"events":[{
    "event_id":"076600bd-4b5d-4f75-9f4b-20964a883f35",
    "occurred_at":1767489400,
    "actor_id":"demo-user",
    "source_ip":"192.0.2.10",
    "country":"GB",
    "kind":"login",
    "success":false,
    "bytes_sent":0
  }]}'
```

`occurred_at` — Unix-время в секундах, `kind` — `api`, `login` или `signup`. Максимум 200 событий в пачке. Ответ 202 означает, что события сохранены; решения рассчитываются отдельно. Повтор ID с тем же нормализованным телом возвращает прежний номер. Другое тело под тем же ID даёт 409 и откатывает всю пачку.

Исторические события разрешены для воспроизведения потока. Время более чем на 30 секунд впереди часов сервера отклоняется. Пример выше исторический: после более нового потока он может получить статус `late`. Для живого потока отправляйте текущее время.

## Решения и повторный прогон

```bash
curl -sS http://localhost:8230/admin/status \
  -H 'X-Admin-Token: local-demo-signalwatch-admin-change-before-deployment'

curl -sS 'http://localhost:8230/admin/runs/00000000-0000-0000-0000-000000000023/decisions?alerts=true' \
  -H 'X-Admin-Token: local-demo-signalwatch-admin-change-before-deployment'

curl -sS -X POST http://localhost:8230/admin/replays \
  -H 'X-Admin-Token: local-demo-signalwatch-admin-change-before-deployment'
```

Постоянный ID основного прогона: `00000000-0000-0000-0000-000000000023`. Replay получает свой ID и фиксированную верхнюю границу событий. `/admin/runs/{id}` показывает курсор и статус; `/digest` считает SHA-256 решений. Для сравнения с live передайте `through`, равный `upper_bound` повторного прогона.

Решение содержит семь признаков, обе оценки и оба порога, `policy`, итоговый `alert` и `model_version`. `reasons` описывает наблюдаемые превышения, а не причинное объяснение Isolation Forest. Оценка модели не является вероятностью атаки.

Ручная проверка: `PUT /admin/runs/{id}/decisions/{sequence}/review`, заголовок `If-Match: 0` для первой записи, тело `{"verdict":"false_positive","note":"Причина решения оператора."}`. Следующая правка требует актуальной версии. Вердикты: `confirmed`, `false_positive`, `needs_context`. История проверок не меняет исходное решение и не переобучает модель.

## Результат сравнения

На dev выбраны **правила**. На позднем test они нашли 85 из 120 размеченных подозрительных событий без ложных тревог среди 6 000 нормальных. Isolation Forest нашёл 57 из 120 и дал 76 ложных тревог. Его тестовый FPR составил 1,27%, хотя на dev порог укладывался в бюджет 1%.

Это синтетический набор со сценарной разметкой, а не данные реальных пользователей. Результат показывает пользу сравнения с простыми правилами; он не доказывает качество защиты реального сервиса. [Методика и ограничения](docs/evaluation.md).

## Проверки

```bash
make check
make test
make smoke
make recovery
make evaluate
```

`make test` использует отдельные PostgreSQL, Redis и RabbitMQ. `make recovery` временно останавливает компоненты этого проекта, очищает его кеш Redis и принудительно завершает worker и dispatcher в проверяемых точках. Журнал сохраняется. Этот сценарий предназначен для локального демонстрационного стенда.

`make evaluate` заново создаёт синтетические данные и артефакты модели. При изменении данных или параметров не подменяйте версию работающего прогона: он связан с прежними моделью и порогами. Обычный запуск использует готовые файлы. Зависимости закреплены в `uv.lock` и `requirements.lock`.

Документация: [архитектура](docs/architecture.md), [эксплуатация](docs/runbook.md), [результаты проверок](docs/verification.md), [объяснение для собеседования](docs/interview.md).

## Границы проекта

Один поток событий, без разделения организаций и высокой доступности. Worker последовательно обрабатывает события каждого прогона. Redis ускоряет чтение окна; при потере кеша окно восстанавливается из БД. RabbitMQ ускоряет запуск обработки; резервный опрос БД позволяет продолжить работу при сбое брокера.

Решения рассчитываются в порядке приёма и не переписываются задним числом. Слишком позднее событие сохраняется как `late`, без тревоги. История растёт; автоматического архивирования нет. Сохраняется не более 20 повторных прогонов.

IP, страна и идентификатор пользователя поступают от доверенного отправителя. Здесь нет GeoIP-проверки, подключения к WAF и автоматической блокировки аккаунтов. На хост опубликован только `127.0.0.1:8230`; у инфраструктурных сервисов нет портов на хосте. Образ приложения запускается без root и без инструментов тестирования.

## Защита тестового окружения

Интеграционные тесты запускаются в отдельном профиле Compose с `TESTING=true`.
Тестовый entrypoint проверяет ресурсы до миграций и seed; непосредственный pytest
проверяет их до импорта приложения. Разрешены только заданные драйвер, хост, порт, имя БД и тестовая роль,
а также адреса брокера, кеша или индекса, если они используются.
Параметры query, фрагменты URL (в том числе пустые), переменные окружения
с неоднозначным регистром имени и переменные `PG*` отклоняются: фактическое подключение не должно отличаться от проверенного URL.
Пароли и полный ошибочный URL в диагностике не выводятся.

Отрицательные проверки можно выполнить без БД:

```bash
uv run pytest --noconftest -p no:cacheprovider tests/test_fixture_safety.py
```

Они запускают настоящий сборщик pytest и тестовые скрипты в subprocess,
запрещают сеть и побочные процессы и проверяют отказ до импорта settings/engine.
Положительная проверка подтверждает сборку штатного профиля без подключения.
Обычные runtime-команды приложения эта защита не меняет. Она предотвращает
ошибку выбора окружения; отдельный Docker namespace и корректные права
тестовых ролей всё равно нужны.

После сборки test-образа `uv run pytest -q scripts/test_test_entrypoint.py` проверяет его настоящий entrypoint: ошибочный флаг `TESTING` или URL не позволяет выполнить даже безвредную выбранную команду. В CI эта проверка обязательна.
