# Эксплуатация локального стенда

Все команды выполняются из папки проекта и относятся только к Compose-проекту `23-signal-watch`.

## Состояние

```bash
docker compose ps -a
curl -sS http://localhost:8230/health
curl -sS http://localhost:8230/ready
curl -sS http://localhost:8230/admin/status \
  -H 'X-Admin-Token: local-demo-signalwatch-admin-change-before-deployment'
docker compose logs --tail=100 worker dispatcher
```

`/health` проверяет доступ API к PostgreSQL. `/ready` проверяет версию основного прогона, его ошибку и свежесть heartbeat worker. Готовность не требует нулевого отставания. `sequence − live.cursor` показывает необработанные события; `outbox.pending` — уведомления без подтверждённой записи об отправке.

Heartbeat обновляется отдельной задачей. Живой heartbeat при неподвижном курсоре и заполненном `error` не означает исправную обработку. Метрики `/metrics` показывают отставание, pending outbox и число решений `scored`/`late` из БД.

## RabbitMQ недоступен

API продолжает принимать события; worker обрабатывает их через резервный опрос БД. Outbox остаётся неопубликованным до восстановления брокера.

```bash
docker compose start rabbitmq
docker compose logs --tail=100 rabbitmq dispatcher
```

Дождитесь уменьшения `outbox.pending` до нуля. Повторно отправлять исходные события не нужно. Некорректные уведомления можно посмотреть через `rabbitmqctl list_queues name messages` внутри контейнера RabbitMQ; для них есть очередь `signalwatch.dead`.

## Redis недоступен или потерял данные

Worker восстановит окно из PostgreSQL. Это может увеличить задержку. Для возврата кеша достаточно `docker compose start redis`; обнулять курсор или менять решения нельзя. Кеш с неверной контрольной суммой, версией или курсором будет проигнорирован.

## Worker или dispatcher упал

```bash
docker compose up -d worker dispatcher
```

Worker повторит незавершённую пачку; её решения и курсор коммитятся вместе. Dispatcher может повторить уведомление после падения между подтверждением брокера и commit outbox. Повторное уведомление не создаёт копий решений.

После аварийной проверки верните задержки в ноль:

```bash
WORKER_BEFORE_COMMIT_DELAY=0 DISPATCHER_AFTER_PUBLISH_DELAY=0 \
  docker compose up -d --no-deps --force-recreate worker dispatcher
```

## Несовпадение модели

Если в логах указано несовпадение версии, восстановите прежние `artifacts/manifest.json` и `artifacts/isolation_forest.joblib` из соответствующего коммита, затем пересоберите контейнеры. Не исправляйте `runs.model_version` вручную: прежние решения рассчитаны по другой версии.

Модель загружается только из доверенного локального артефакта. Хеш обнаруживает порчу файла, но не делает чужой pickle безопасным. Смена модели живого потока требует отдельной миграции, которой в этой версии нет. Новый replay может быть создан с текущей загруженной моделью для отдельного сравнения.

## Событие получило late

Проверьте его `occurred_at` и watermark прогона. Опоздание более 30 секунд сохраняется без оценки. Это правило воспроизведётся и в replay. Смена порядка событий ради исчезновения `late` меняет смысл исходного потока и не является восстановлением.

Для исторического demo-потока используйте свежий стенд либо уже загруженный поток с теми же UUID. Если до первого demo принять современные события, старые demo-события будут поздними. Повторный запуск smoke не очищает историю.

## Рост истории и остановка

После 20 replay API возвращает 409. Автоматического удаления нет; архивирование требует согласованного обслуживания строк прогона, решений и ручных проверок. Не удаляйте события, на которые опираются существующие решения. Для демонстрации обычно достаточно нескольких прогонов.

```bash
docker compose --profile test stop test-db test-redis test-rabbitmq
docker compose stop
```

`make down` удаляет контейнеры и сеть, сохраняя именованные volumes PostgreSQL и RabbitMQ. `docker compose down -v` удаляет данные и подходит только для намеренного сброса стенда. Кеш Redis можно восстановить из PostgreSQL.
